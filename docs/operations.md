# Nekodex 运行手册

> 本手册描述当前待退役实现。新的运行方式将按 [简化监控架构](simplified-monitor-architecture.md) 改为“来源电脑本机文件只读采集器 + HTTP 状态接口 + PC/Poke3 统一前端”。迁移完成前，不再围绕共享 daemon、独立 App Server、事件回放或来源重启扩大排障和功能。

本文面向首批支持环境：NixOS/Linux 来源电脑与 Poke3 Android 10 监控端。Nekodex 当前只读，不会远程创建、发送、停止任务或处理审批。

## 当前 M1 运行方式

M1 的实际运行入口是来源电脑上的 `tools/codex-status-server.py`，不是本手册后文的 8788 设备组服务。它只读本机 `CODEX_HOME`，通过 HTTP 提供 `/healthz`、`/api/status` 和 `/api/sessions`；Tauri/Android 接入仍属于 M2，Poke3 单来源局域网交付属于 M3。

在来源电脑执行：

```bash
CODEX_HOME="$HOME/.codex" \
CODEX_STATUS_WORKSPACE="$PWD" \
CODEX_STATUS_TOKEN="choose-a-private-token" \
python3 tools/codex-status-server.py --host 0.0.0.0 --port 8765
```

浏览器访问 `http://<来源电脑>:8765/` 并输入令牌。若只在本机检查，可绑定 `127.0.0.1`，此时不需要令牌。M1 的验证和边界见 [实现状态](implementation-status.md) 与 [简化监控架构](simplified-monitor-architecture.md)。

以下章节中的 `8788`、mDNS、设备组成员名册、来源重启和 App Server 均属于旧实现迁移资料；不要用它们判断 M1 是否可用。

## 旧设备组首次使用（历史）

1. 在一台设备上打开“设备组”，设置本机名称并创建设备组。
2. 选择“邀请新设备”，在 10 分钟有效期内让另一台设备通过附近发现或 `IP:8788` 连接，并输入 8 位加入码。
3. 邀请端核对新设备屏幕上的名称与设备 ID，再接受加入。
4. 加入完成后成员名册会通过认证连接传播；任意在线成员可以继续邀请设备，不依赖最初创建组的设备在线。

加入码只用于本次限时邀请。不要截图、记录到日志或交给设备组之外的人。设备组成员可以读取组内来源电脑公布的监控数据，并可以邀请或移除其他成员，因此只加入个人信任设备。

## 旧设备组网络要求（历史）

- Nekodex 固定监听 TCP 8788，用于认证后的 Noise 加密直连。
- 附近发现使用局域网 mDNS；网络需允许组播和 UDP 5353。
- 访客网络、客户端隔离、跨 VLAN 或防火墙阻断组播时，附近发现可能不可用；仍可在已知地址时手工输入 `IP:8788`。
- 端口占用会作为错误显示，应用不会静默换成随机端口。

公开候选地址和 mDNS 信息不授予访问权限。业务连接仍须验证设备身份、设备组成员资格和协议能力。

## 旧来源电脑实现（历史）

Linux 电脑可以提供额度、活动、项目、会话和待审批状态。Poke3 只查看数据，不运行 Codex。

- “共享实时来源”连接已经运行的官方 Codex App Server daemon，可观察该 daemon 已加载会话的实时状态。
- “历史回退来源”使用独立只读 App Server，可靠读取额度和持久化历史，但不会把不可见的实时状态或审批误报为空。
- 启动共享 daemon 是来源电脑上的明确本机维护操作；失败时 Nekodex 保留回退来源并显示原因，不会绕过系统包管理。
- 项目白名单只能在来源电脑本机维护。目录会转换为真实绝对路径，并拒绝重复或父子嵌套项目。

审批页只用于监控。任何审批都必须回到对应来源电脑的 Codex 客户端处理。

## 后台运行

- Linux：关闭主窗口只会隐藏窗口，设备组和来源任务继续运行。通过系统托盘重新打开；需要完全退出时使用托盘的“退出 Nekodex”。
- Android：通知对应前台连接服务。普通返回桌面后仍维持设备组连接；系统强制停止、系统回收和设备重启后的行为以当前验收状态为准。
- 页面不可见时统一前端暂停多数轮询；重新前台会触发局域网连接复核。

## 常见状态

- “设备在线”只表示认证组网连接正常，不保证该设备的 Codex 来源可读。
- “来源不可用”表示本次实时读取失败；如果存在按来源隔离的缓存，页面会显示缓存采集时间。
- “版本不兼容”需要升级对应设备；页头显示实际运行的 Nekodex 版本。
- “活动历史不完整”表示事件游标出现缺口或恢复失败；应用会尝试有界回放，不会把缺口当作成功。
- “身份验证失败”不会通过重试降级为未认证连接。确认设备仍在名册后，检查两端时间、网络和版本。

## 恢复顺序

1. 先让应用回到前台，等待一次连接复核。
2. 在设备组页面刷新连接状态；确认 TCP 8788 未被其他程序占用。
3. 若只有来源数据失败，在来源电脑本机重启来源服务，不要退出设备组。
4. 若附近发现失败但地址已知，使用手工直连。
5. 身份确实丢失或应用被卸载后，以新设备身份重新加入，并由现有成员撤销旧身份。

不要通过删除数据库、清除应用数据或卸载重装来处理普通网络故障。这些操作会破坏本机成员状态，且 Android Keystore 身份不可从自动备份恢复。

## 数据与升级边界

- 设备组数据库迁移在单个 SQLite transaction 中完成，最后才更新 schema 版本；不支持把新 schema 降级给旧版本。
- Android 自动备份已关闭，避免只恢复数据库而没有对应 Keystore 私钥。
- 正常升级必须保留包名和签名，并提高 `versionCode` 后覆盖安装。
- 离线缓存上限为 100 MiB，可从来源重新采集；它不是任务或仓库的备份。

签名、版本、升级与制品规则见 [release-and-upgrade.md](release-and-upgrade.md)，当前运行证据和未完成验收见 [implementation-status.md](implementation-status.md)。
